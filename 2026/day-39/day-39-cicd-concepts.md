# Day 39 – CI/CD Concepts

# Task 1 – The Problem

## Scenario

A team of five developers is working on the same project. Each developer pushes code to the same GitHub repository and manually deploys the application to production.

### 1. What can go wrong?

Many problems can occur during manual deployments:

- Developers may overwrite each other's changes.
- Bugs may reach production because there are no automated tests.
- Different developers may use different environments.
- Manual deployment steps can be forgotten or executed incorrectly.
- Rollbacks become difficult if something breaks.
- Deployments take more time and are prone to human errors.

---

### 2. What does "It works on my machine" mean?

"It works on my machine" means that the application runs correctly on a developer's local computer but fails on another developer's system or on the production server.

This usually happens because of differences in:

- Operating System
- Software versions
- Installed packages
- Environment variables
- Configuration files

CI/CD helps solve this problem by building and testing the application in a consistent environment.

---

### 3. How many times a day can a team safely deploy manually?

Manual deployments are usually slow and risky. Most teams can safely deploy only a few times a day because each deployment requires manual testing and verification.

With CI/CD, deployments can happen many times a day because the build, testing, and deployment processes are automated.

# Task 2 – CI vs CD

## 1. Continuous Integration (CI)

Continuous Integration is the practice of frequently merging code changes into a shared repository. Every code change automatically triggers a build and tests to detect bugs early before they reach production.

### Real-World Example

A developer pushes code to GitHub. GitHub Actions automatically builds the application and runs unit tests. If any test fails, the developer is notified immediately.

---

## 2. Continuous Delivery (CD)

Continuous Delivery automatically prepares the application for deployment after all tests pass. However, the final deployment to production still requires manual approval.

### Real-World Example

A company automatically builds and tests every release. After everything passes, the release waits for the DevOps engineer to click **Approve** before deploying to production.

---

## 3. Continuous Deployment

Continuous Deployment goes one step further than Continuous Delivery. After all tests pass successfully, the application is automatically deployed to production without any manual approval.

### Real-World Example

A developer pushes code to GitHub. The application is built, tested, and automatically deployed to production if every stage succeeds.

---

## Difference Between CI, Continuous Delivery, and Continuous Deployment

| Continuous Integration | Continuous Delivery | Continuous Deployment |
|-------------------------|--------------------|-----------------------|
| Automatically builds and tests code | Automatically prepares code for release | Automatically deploys code to production |
| Detects bugs early | Requires manual approval before production | No manual approval required |
| Developers integrate code frequently | Production deployment is controlled | Production deployment is fully automated |

# Task 3 – Pipeline Anatomy

A CI/CD pipeline is made up of different components that work together to automate the software delivery process.

## 1. Trigger

A trigger is the event that starts the pipeline.

### Examples

- Push to GitHub
- Pull Request
- Scheduled job
- Manual trigger

**Example:**

A developer pushes code to the `main` branch. This automatically starts the pipeline.

---

## 2. Stage

A stage is a logical phase in the pipeline.

Common stages are:

- Build
- Test
- Deploy

Each stage groups related jobs together.

---

## 3. Job

A job is a set of related tasks executed within a stage.

**Example:**

Build Stage

- Install dependencies
- Build the application
- Create Docker image

These tasks together form one job.

---

## 4. Step

A step is a single command or action inside a job.

Examples:

```bash
npm install
npm test
docker build -t myapp .
```

Each command is considered one step.

---

## 5. Runner

A runner is the machine that executes the pipeline jobs.

Examples:

- GitHub Hosted Runner
- Jenkins Agent
- Self-hosted Runner
- Azure DevOps Agent

The runner performs all build, test, and deployment tasks.

---

## 6. Artifact

An artifact is the output generated by a job.

Examples:

- Docker Image
- JAR file
- ZIP package
- Build reports
- Test reports

Artifacts are stored and used in later stages such as deployment.

# Task 4 – CI/CD Pipeline Diagram

## Scenario

A developer pushes code to GitHub. The application is automatically tested, built into a Docker image, and deployed to a staging server.

## Pipeline Diagram

```
                Developer
                    │
                    ▼
          Push Code to GitHub
                    │
                    ▼
        ┌────────────────────┐
        │      Trigger       │
        │   Git Push Event   │
        └────────────────────┘
                    │
                    ▼
        ┌────────────────────┐
        │   Stage 1: Build   │
        │ Install Dependencies│
        │ Build Application   │
        └────────────────────┘
                    │
                    ▼
        ┌────────────────────┐
        │   Stage 2: Test    │
        │ Run Unit Tests     │
        │ Run Lint Checks    │
        └────────────────────┘
                    │
                    ▼
        ┌────────────────────┐
        │ Stage 3: Package   │
        │ Build Docker Image │
        │ Push to Registry   │
        └────────────────────┘
                    │
                    ▼
        ┌────────────────────┐
        │ Stage 4: Deploy    │
        │ Deploy to Staging  │
        └────────────────────┘
                    │
                    ▼
             Application Ready
```

## Pipeline Flow

1. Developer pushes code to GitHub.
2. GitHub triggers the CI/CD pipeline.
3. The application is built.
4. Automated tests are executed.
5. A Docker image is created.
6. The Docker image is pushed to a registry.
7. The application is deployed to the staging environment.
8. The deployment is verified.

### 1. What triggers the workflow?

The workflow is triggered whenever code is pushed to the **main** branch or when a **Pull Request** is created for the main branch.

---

### 2. How many jobs does it have?

The workflow performs multiple CI jobs, including:

- Lint & Format
- Security Scan
- Run Tests
- Build Docker Image

---

### 3. What does it do?

The workflow automatically checks the quality of the code before it is merged.

It performs the following tasks:

- Checks code formatting
- Runs linting
- Performs security scanning
- Executes automated tests
- Builds a Docker image

This helps developers identify issues before deploying the application.
